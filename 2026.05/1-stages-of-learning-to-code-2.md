# 我学习编程的几个阶段（二）

我感谢喜欢写文章的自己，25年三月我写了这篇文章 [我学习编程的几个阶段](https://zhuanlan.zhihu.com/p/27396125221)， 从现在的角度看这个文章很有考古意义：比较忠实地记录了前 AI 时代的我是如何学习古法编程的。

之所以感谢自己是因为，现在26年五月，我已经几乎彻底忘记我是怎么学习过来的了，当时写的这篇文章对现在以及以后的我都有非常大的意义，这类文章很容易引起我对 “一个人应该如何成长” 相关的思考，一个优秀的成长模式不仅能够影响我带新人，也会影响我自己的发展。

一年倏忽，我的编程能力又有许多进步，特此记录。

当然我们仍然只谈编程。

## 工程化

工程化是上一篇文章的结尾，现在处理工程化问题对我来说已经是信手拈来，尤其是我从 [gitea](https://github.com/go-gitea/gitea) 的源码中学到了很多，包括如何规范地使用 github actions，makefile，以及进行测试。

当前我主要关注的工程化问题是，如何让 AI 更高效地参与软件开发。最近一年出现了许多诸如渐进式披露，human in loop， 让 AI 获取反馈，通过静态分析等检查机制来规范 AI 行为 ... 等等思潮，其实实际上大多是和前 AI 时代的工程化思路是差不多的，尤其是静态检查，大体方向就是把 AI 当做一个提交 PR 的陌生人来约束即可，以及你需要提供优质的文档方便 AI 查阅，给AI提供充足的上下文等等。虽然现在 AI 已经很高效了，但是我总觉得效率方面还可以再更进一步，现在的 harness 工程绝对没有达到最终形态。

## 解耦

我对解耦的领悟晚的出奇，我真的花了很多年的时间去领悟解耦，并非是磨洋工的花时间，而是我每次写项目真的都会写到一定程度就会复杂度高到难以为继，在一个又一个项目中我像西西弗斯一样用尽全力去思考文件结构，代码组织，设计模式。 最后的答案非常的简单却又合理：依赖倒置。

对设计模式的“知道”，“理解”，“应用”完全是不一样的事，我早就接触过设计模式，但是一直没有学会，最终让我拨云见日的是我偶然一次使用了 nestjs 框架，它的依赖注入模式让我觉得赏心悦目，同时我在另一个前端项目中也首次尝试使用了 vueuse 中的事件总线，然后我就意识到，我终于学会解耦了。

## 读源码

我并不是有意识的奔着一个明确的“学会解耦”这个目标去奔跑，而是我只知道有问题，但却形容不出来。如果给当时的我自己一些建议，我会说：

> 写项目写不下去就看书，看书和写项目都遇到困难就读别人项目的源码。

我过去很少看源码，这实质地影响了我的进步，本篇文章所谈到的大部分进步都是经历了非常久的阻塞之后，在读了源码之后终于开智的。

“写项目写不下去就看书、看书也看不懂就去读源码” 这个逻辑是我从知乎学到的，我曾经就像一个“云玩家”在知乎上读了很多关于程序员成长的感悟，但自己没有实际到达过相应的水平，就像一个小孩去读朱自清的背影，读项脊轩志，没有对应的人生经历是不会有切实的感受的。当我重新发现了前人留下的记号，一股难以言说的复杂情绪涌上心头，也许我的文章也会成为别人的记号，没有太多指导意义但是会让他印象深刻。

## 接口设计

我对接口设计的理解发生了变化，我最早认为的接口设计很简单，就是每个模块只暴露 interface，其他模块只依赖 interface 而不依赖实现，从而实现解耦 —— 这句话是没错的，但问题是太浅薄了。世界上有非常多正确的废话，这就是其中之一，思路是对的，但不能解决问题。

我们来把上面的理解称作“理解一”，下面的问题称作“问题一”：假如你目前只想先开发一个实现，时间不允许你一口气开发出两到三个实现，那么你的接口是不是会和目前唯一的实现完全一致？如果不完全一致，你如何预测未来的其他实现的细节来调整你的接口？如果我对未来实现的判断有误，接口设计的不好是不是还要再改？这是我曾经真实思考过的问题。

解决上面的问题不需要否定“理解一”，而是需要转换视角，其实 “问题一” 的出发点都是错误的，提问者仍然站在先有实现再有接口的思维方式上，而不是发自内心的认为先有接口再有实现，他（也就是过去的我）为了遵循“理解一”，明明已经构思出了一个实现，再额外去为了实现去想如何开发一个接口，才会提出这样的问题，实际上 “如何设计接口” 和 “如何开发实现” 的关联并没有那么大，而是和需求有关联，是根据需求去设计接口，再根据接口去设计实现，上面的思路是完全本末倒置的。

出发点的错误导致他甚至会考虑在接口设计好之后再进行调整。如果需求有变动，应该开发新的接口而不是替换原有接口。就像 linux 的图形技术栈里，由于现实世界 GPU 技术的发展，内核开发了新的 DRM 接口，旧的 framebuffer 接口只是被标记为废弃，而不是直接删除。

我们将新的理解称为“理解二”，我暂时也只是待在 “理解二” 的水平，没办法分享更高级的理解了，但是我可以说说我是如何晋升到理解二，以及我现在遇到的问题。

### 如何升级理解

为什么我上面已经明明说出了理解一和理解二，却还要再解释如何升级理解？因为读者不可能因为我的分享而顿悟，我只能启发你的思路，匮乏的文字不能表达我获得新理解的感受的十分之一，无法通过文字就完全把我当时的突破就说给你听，不是我不愿意，是不可能，因为我只能分享我最后补上的是哪一块临门一脚，每个人缺的地方都是不一样的，我没办法把我过往的整个学习经历都写出来让你再走一遍和我一样的路，无论是对你还是对我都是不切实际的。

我最后的临门一脚就是读源码，在积累了大量的挫败经验，心里积累了非常多的错误思考之后，最终终于想到读源码来学习别人的正确实践是怎么做的，上面提到的工程化问题我是通过 gitea 学的，接口设计相关的理解我是通过 nestjs 学的。

nestjs是一个非常注重接口设计的框架，它内置了依赖注入和控制反转并使用到了整个框架的接口。（我并没有真正的去读nestjs的源码，但是我通读了他的文档学习了他的设计思路）

我接触过很多web框架，包括：
1. fastAPI，其实 fastAPI 也有很不错的依赖注入，但是当时我没有接触到，我只觉得这是一个轻量灵活的 web 框架
2. django，这是一个大而全的框架，很多功能都有现成工具可用。
3. trpc，这个框架有浓厚的 开发体验优先 的风格，和我后来了解到的 elysia 很像。
4. fastify，这个框架有浓厚的函数式风格。
5. nuxt，主要特色是多种部署和渲染方式，丰富程度中等的 module 系统，以及约定大于配置设计风格。

简直就像神农尝百草。

这些框架各有特色和设计风格，但是都没有解决一个问题：代码多了会乱。直到我遇到了 nestjs 的面向切面和依赖注入，这才让我对接口设计入了门，我开始明白如何控制复杂度，这是第一步。

第二步你需要有一些阅读常见架构设计的经验，软件架构要从多层次、多流程、多个时态去理解，我想在这里聊聊 gitea 的SSR、测试和生产环境的不同构建流程，nestjs 的请求生命周期，尤其nest这个例子能很好的说明什么叫多层次、多时态、多流程地理解架构，因为 app、module、request 天然分层的同时又有各自的生命周期流程，同时各自生命周期内还在维护不同的数据流，但是由于我已经有一段时间不用 nest，不太能脱稿即写，以后再更新这块吧。

第三步

后来我研究过 linux 的图形技术栈，也自己尝试过仿照我上面说的“多层次、多流程、多时态”的去设计一个架构（graph 构建框架），以及最近在尝试在生产环境使用k8s，我对接口设计又有一些新的理解。

对一个新手来说，接口本身是不干什么事情、看似没有什么实际作用，还在到处使绊子。就像一个新学 k8s 的人可能会觉得为什么端口转发这么简单的事情，在k8s里面要进行非常多的配置，又是 ingress 又是 service；docker里创建数据卷非常的简单直接，k8s里面又要PVC、PV、还要 storageClass，其实这复杂的配置正是 k8s 接口设计功力的高深之处；linux 同理，图形栈也定义了非常复杂的接口，关于内核我最常听到的词就是“内核接口”，对于内核来说同样最重要的也是接口而不是实现，接口确实不进行什么实际的操作，但是在这种大型系统里解决了最重要的问题，学习linux图形栈让我理解了这一点。

**我前面提到接口设计不是先有实现再有接口，而是先有需求、再有接口、再有实现，接口设计实际上是服务于整个系统的，所有接口合在一起，实际上是在定义整个系统的规则，所有实现必须按照规则进行工作，接口设计的本质是，发现实现该需求会有什么主要问题，解决问题需要哪些参与要素，然后为每个参与要素设计一个接口，并把一套接口组合成一条解决该问题的路径。然后实现层面再按照这个路径去走，就能实际的解决问题。**

这就是我理解的接口设计的本质 —— 但是即使我像这样展开说明，对别人来说可能仍然如读天书，因为我只是分享了我的体验，而不是实际的去告诉你 linux 内核是什么样子、我前面说的web框架是怎么设计接口的、k8s的接口是什么样子的、我在设计自己的架构的时候思考过哪些问题，因为缺乏类似的经历而不能真正的共鸣。
