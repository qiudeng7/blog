# 有了 AI 之后，我可能再也不会重构了

最近在做一个软件工程项目时，我突然意识到一件很有意思的事情：**在 AI 编程足够便宜、足够快之后，“重构”可能不再总是最划算的选择。**

我的开发习惯基本是先把架构图和流程图定下来，再让 AI 去实现。项目最初的几个版本通常都很干净，因为需求明确、架构明确，AI 只需要按照设计把代码写出来。

真正的问题出现在后面。

软件不可能永远停留在最初的设计里。需求不断增加，原来的假设逐渐失效，为了赶进度又会不断在已有结构上打补丁。每一个补丁单独看可能都很合理，但它们叠加起来以后，代码库就会慢慢变得混乱。

传统软件工程在这个时候通常会告诉我们：该重构了。

但我最近发现，**用 AI 重写，可能真的比重构快很多。**

## 从最后一个干净的 commit 重新开始

假设一个项目的 Git 历史大概是这样的：

```text
A -- B -- C -- D -- E -- F -- G
          ↑                 ↑
      最后一个干净版本      当前版本
```

从 `C` 到 `G` 的过程中，我们增加了很多功能，同时也积累了很多妥协、错误设计和临时补丁。

传统的做法，是站在 `G` 上一点一点整理代码：拆模块、改接口、迁移数据结构、删除历史包袱，同时还要尽量保证行为不发生变化。

这件事麻烦的地方在于，**重构天然需要理解历史。**

你不仅要知道现在的代码是什么样，还要理解为什么会变成这样；不仅要知道哪些代码应该保留，还要判断哪些东西只是历史遗留。很多时候，重构真正昂贵的并不是“写代码”，而是在一个已经复杂的系统里区分哪些复杂度是业务本身需要的，哪些复杂度只是实现过程中产生的垃圾。

而如果 AI 写代码已经足够快，另一条路线突然变得很有吸引力：

找到最后一个还算干净的 commit，例如 `C`，然后把 `C -> G` 之间真正有价值的需求和实现重新梳理一遍，让 AI **以 C 为基础重新实现一次。**

不是修补 G。

不是把 G 一点点整理成理想状态。

而是把后来已经验证过的需求，当成一份新的、更加完整的需求文档，再实现一次。

## 第二次实现拥有第一次没有的信息

第一次从 `C` 写到 `G` 时，我们其实不知道最终会变成什么样。

很多设计只能根据当时的信息决定。后来的需求出现以后，只能继续兼容旧设计，于是系统逐渐长出各种特殊分支和补丁。

但是第二次实现的时候不一样。

此时 `G` 已经存在了。

我们已经知道最终有哪些功能，知道哪些抽象后来证明是错误的，知道哪些接口不断被绕过，也知道哪些地方因为需求变化被反复修改。

换句话说，第一次开发是在**预测未来**，第二次开发是在**总结历史**。

这两件事情的信息量完全不同。

我们甚至可以让 AI 直接比较最后一个干净的 commit 和最新 commit 之间的变化：哪些能力是后来增加的，哪些设计在过程中发生了扭曲，哪些实现明显只是为了迁就旧结构而存在。

然后把这些已经被现实验证过的需求，一次性放进新的设计里。

从这个角度看，重写并不一定是在“重新做一遍以前做过的工作”。它更像是利用第一次实现获得的信息，进行第二次、信息更加充分的实现。

## Git 历史开始有点像 append-only 数据库

想到这里，我突然觉得以后自己的 Git 分支可能会越来越像某些 append-only 数据库：

**只有 insert，没有 update。**

当然这只是一个夸张的比喻。日常的小修改、小重构当然不会消失，我也不可能因为一个函数写丑了就把整个项目重写。

真正变化的是面对**结构性技术债**时的决策。

以前我们的默认思路通常是：

```text
旧系统
  ↓
不断修改
  ↓
逐步重构
  ↓
新系统
```

但 AI 让另一种工作流开始变得现实：

```text
干净版本 C ───────────────→ 重新实现 H
     │                         ↑
     └→ D → E → F → G ─→ 提取最终需求
```

`D、E、F、G` 并没有白写。

它们完成了一个非常重要的任务：**探索需求。**

它们证明哪些需求是真实存在的，暴露哪些设计是不合理的，也让我们知道项目最终到底需要长成什么样。

然后我们不再要求这些探索过程产生的代码必须永远活下去。

代码可以被抛弃，但从代码和 Git 历史中获得的信息不会被抛弃。

## AI 改变的可能不是编码速度，而是代码的折旧速度

以前我们不愿意重写，一个非常现实的原因是代码太贵了。

一个工程师花几个月写出来的几万行代码，即使里面已经有不少历史包袱，也很难有人轻易说“扔掉重新写”。Joel Spolsky 那篇著名的《Things You Should Never Do》之所以反对重写，本质上也是因为旧代码里沉淀着大量不容易被重新发现的知识。

这个判断到今天仍然非常重要。**如果你不知道旧系统为什么这么写，贸然重写依然非常危险。**

但 AI 改变了其中一个变量：重新实现代码本身的成本正在快速下降。

于是问题开始从：

> 这么多代码，怎么舍得重写？

变成：

> 旧代码里真正不能丢失的信息，到底是什么？

如果需求、行为、边界条件、测试、历史决策都能够被可靠地提取出来，那么代码本身可能越来越像一种可再生资产。

真正昂贵的不再是那几万行字符，而是隐藏在它们背后的**需求和判断。**

这可能也是 AI 编程带来的一个很有意思的变化：我们过去一直在想办法延长代码的寿命，而未来也许会逐渐接受——**代码本来就是会折旧的。**

当重新生成代码的成本足够低时，与其不断维护一栋被反复加建的老房子，有时候根据已经明确的需求重新画图、重新盖一栋，反而更简单。

所以我现在有一个很极端、但我觉得越来越可能成立的想法：

**以后的 Git 里，也许只有重写，没有重构。**

至少，当下一次面对一个已经被补丁堆得非常混乱的代码库时，我会先问自己一个以前很少会问的问题：

**为什么一定要救这份代码？**
