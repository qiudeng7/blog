## 问题

我正在对数据库进行压测, 尝试探索数据库的极限, 但是我慢慢发现问题不在数据库服务端的承受能力, 而在于客户端的并发能力, 原因是客户端不只是要发压, 还需要记录各种指标和写日志, 由于我糟糕的设计能力, 客户端的效率非常拉胯. 我逐渐从 python 异步转向多进程, 榨干单机性能后又试图转向分布式, 在这一步我的代码库彻底难以为继了.

往前看: 新写的功能, 多进程和分布式, 实现既不规范, 跑起来也不稳定, 实现思路其实也有点问题, 然稍微哪里有点异常情况就报错, 要在代码里加额外的分支情况处理;

往后看: 多进程异步虽然能跑但是混乱不堪, 光异步还能看, 异步+多进程就已经能跑但是没法看了, 加个新的多机并发就完全是防御性编程; 还有些地方是我小规模重构过的, 看起来似乎很干净, 但是重构这件事情本身就会带来不一致性, 已经重构的部分和没重构的地方会地方不一致, 这导致了整体的进一步复杂化.

我遇到过太多次类似的情况, 难道就不能根治吗 ?

## deprecated 思路

这个思路我称之为 deprecated 思路, 因为即使是我非常早期的浅薄 java 开发经历, 都见过非常多的 `@deprecated` 注解. 这个思路大致是:

代码只能加, 可以注入, 可以deprecated, 可以打补丁, 但是不要改.

这解决了前面的重构导致的不一致问题, 而且工作量小, 但是屎山会越堆越大. 

我想了想, 这不就是国内 "能跑就行" 的码农思想吗, 断不可行. 但 deprecated 还是可用的, 兼容历史接口是一个很好的做法, python 生态的框架在这方面做得很不好.

## 新的理解

参考 nestjs 的请求生命周期和依赖注入的接口设计, 我理解了我项目的混乱根源和正确做法.

正确的做法是, 比如有 A B C, 三处代码, B 依赖 A, A 和 B 都是某个 interface 的实现, C 可能是某个 entrance 或者 workflow, C 来负责构造 A 然后注入到 B, B 只需要声明依赖, 此时对 C 来说就是非常简单的实现了一个流程图, 如果需要另一种测试场景就添加一个新的流程, C 来负责构造不同场景下的的 A 和 B 不同实现, B 不需要关心 A 的不同实现.

**依赖注入模式的关键是让 B 把所有的依赖项打包起来统一声明,  C 来负责具体的依赖注入, 而不是让 B 去关心应该访问哪一个具体的依赖, 这会增加 B 的复杂度.**

我们的概念中只包含三个简单的要素和三个关系:
1. A: 一个功能模块, 他只需要实现自己的功能, 不需要关心和其他模块的关系.
2. B: 一个依赖A的功能模块, 他只关心 A 的接口, 或者说关心 A 的抽象 ( 但是要警惕抽象会遮蔽真实的过程), 以及自己的功能.
3. C: 它会访问具体的模块, 完成依赖注入, 并实现某个流程.
	1. 实际上在 nestjs 中注入的过程也不由 C 来完成, 是由容器完成.

这很像我之前学到结构化编程, 虽然现代语言都是顺序结构, 分支结构, 循环结构, 但是这是因为有人证明过只需要这三种结构就可以实现所有逻辑, 在结构化编程之前都是各种有条件跳转, 无条件跳转和递归之类的代码. 结构化编程最终把编程逻辑简化成了三个简单的结构, 用这三个结构能够表达出之前的所有混乱表达.

依赖注入模式同理, 它用上面的简单结构解决了依赖和模块化问题, 让每个系统内部变得更加简单.


在具体实践上, 我有两个初步的思路, 一种是用静态分析工具, 强制分析我的整个项目的 import 关系, 是否符合这个简单的定义, 但可以想见这种工具的最大问题是每增加一个新的模块我们都需要手动约束它的关系.

另一个思路就是模仿 nestjs, 在写代码之初就使用依赖注入框架来声明依赖, 以及实现依赖注入, 但缺点是有侵入性, 上一种思路是对代码库无侵入性的.

为了把这两种思路代入实践, 我还需要做两件事:
1. 进一步比较这两种思路在工程实践上的优劣
2. 学习现实中的框架
### 实践思路对比

| 维度    | 静态分析工具                                                                  | 依赖注入框架                                                          |
| ----- | ----------------------------------------------------------------------- | --------------------------------------------------------------- |
| 核心思想  | 事后审计，强制执行规则                                                             | 事前约束，框架引导架构                                                     |
| 侵入性   | 无侵入（或低侵入）                                                               | 高侵入                                                             |
| 实施时机  | 开发后期/CI阶段                                                               | 开发初期                                                            |
| 学习曲线  | 低（只需理解规则）                                                               | 高（需学习框架范式）                                                      |
| 团队接受度 | 阻力较小                                                                    | 可能需要培训                                                          |
| 优势    | 1. 可渐进式实施，先宽松后严格<br>2. 可针对不同模块设置不同规则<br>3. 能发现“意外”的依赖违反                 | 1. 事前预防：不正确的依赖无法编译/运行<br>2. 明确声明：依赖关系一目了然<br>3. 框架保证：架构一致性由框架保证 |
| 劣势    | 1. 事后发现：代码已写完，修复成本高<br>2. 规则逃逸：开发者可能找到绕过规则的方法<br>3. 误报问题：某些“合理”的依赖可能被误判 | 1. 过度约束：可能限制合理的架构创新<br>2. 框架锁定：整个项目绑定到特定框架                      |

那么如果使用混合思路呢? 混合思路的目标是 结合静态分析工具和依赖注入框架的优点，同时尽量减少它们的缺点。

混合思路的核心是：**在项目不同部分或不同阶段，采用不同的策略**。

例如：
1. 新模块使用 DI 框架，旧模块使用静态分析工具逐步改造。
2. 核心业务层使用 DI 框架保证架构，工具类或第三方集成使用静态分析工具。
3. 开发阶段使用 DI 框架，CI 阶段使用静态分析工具进行额外检查。

但是混合思路会导致这个工具的使用和本身的实现都会变得无比复杂, 混合思路是完全不必要的.


## 现实中的框架: nest 和 rx

了解了一圈 DI 框架, 其实都和 nestjs里的 DI 差不多, 但值得一提的是 nest不仅仅有 DI, 还有 rx.

rx 是一个响应式编程库, nest 通过它来把我前面说的流程图落地为"代码 C", 通过 rx 可以定义一条 **异步数据流管道**. 这解决了我“代码块C”如何具体落地的问题：在NestJS中，C常常不是一个独立的组装模块，而是“DI容器”与“响应式数据流”共同构成的执行环境。业务逻辑被表达为对数据流的转换，而所有依赖都已预先由容器备好.

## 是否要用 DI 框架

**我发现一个悖论: 如果你已经能够掌握依赖注入的奥义, 那么你不需要使用这类框架. 如果你没有掌握依赖注入, 你会觉得依赖注入写起来又臭又长且过度设计.**

框架只是一个帮你更优雅、更自动、更少犯错地实现这条流水线的工具。选择哪种工具，取决于你的语言、团队、项目阶段和对“约束”的接受程度。

所以通常来说依赖注入框架的适用场景是团队协作, 但现在即使是个人开发者也大多使用 coding agent, 显式的 DI 可以让 agent 更容易写出规范的代码.
